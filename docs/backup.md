## 1. Что бэкапится

Один прогон создаёт **две независимые части**, чтобы можно было восстановить только БД или только картинки:

| Файл | Содержимое | Как создаётся |
|---|---|---|
| `db_<дата>.sql.gz` | полный дамп MySQL: структура + данные всех таблиц | `mysqldump --single-transaction --quick --routines --triggers --no-tablespaces --default-character-set=utf8mb4` |
| `images_<дата>.tar.gz` | архив каталога загрузок (`app.storage.upload-dir`, в проде `/app/img/images`) | потоковый tar.gz, записи внутри — `images/<путь>` |

`<дата>` — момент старта прогона в формате `yyyy-MM-dd_HH-mm-ss`, например `2026-10-25_21-59-19`.
По этому префиксу части одного прогона сопоставляются друг с другом.

Важно:

- Дамп снимается в режиме `--single-transaction` (консистентный снимок InnoDB без блокировки таблиц).
- Пароль БД не попадает в аргументы процесса: он передаётся через переменную окружения `MYSQL_PWD`.
- Если архив картинок отключён (`app.backup.include-images=false`) или каталог загрузок не существует,
  создаётся только дамп БД — это не ошибка, копия считается неполной (в UI статус «Неполная»).
- Пустой дамп (0 байт) считается ошибкой: прогон помечается `FAILED`.

## 2. Как устроено: три пути запуска

| Путь | Что запускает | Когда работает | Где настраивается |
|---|---|---|---|
| Кнопка «Создать бэкап» | `POST /admin/backup/create` → `BackupWorker` в отдельном потоке | пока приложение живо, admin-сессия | админка → Настройки → Бэкап |
| Планировщик в приложении | `BackupScheduler` (`@Scheduled`) | если включён чекбокс и задан токен | `app.backup.cron` + чекбокс в админке |
| Cron на сервере | `scripts/backup.sh` | даже если приложение упало | crontab на сервере |

Все три пути используют один и тот же Яндекс.Диск и одинаковые имена файлов (`db_<дата>.sql.gz`,
`images_<дата>.tar.gz`), поэтому копии, сделанные cron-скриптом, видны в админке и участвуют в ротации.

**Взаимное исключение.** Бэкап и восстановление защищены общим семафором (`BackupOperationLock`):
одновременно может идти только одна операция. Второй запуск (кнопка в момент cron/планировщика или
восстановления) получает понятную ошибку «Уже выполняется бэкап или восстановление». HTTP-запрос при
этом не висит: создание и восстановление выполняются асинхронно, UI опрашивает статус.

## 3. Быстрый старт

### 3.1. Приложение на Яндекс.Диске

1. Откройте <https://oauth.yandex.ru/> → «Создать приложение» → тип «Для доступа к API».
2. В правах отметьте:
   - `cloud_api:disk.read` — читать Диск (список копий, скачивание, восстановление);
   - `cloud_api:disk.write` — писать (загрузка, создание папки, удаление).
3. В поле «Redirect URI для веб-сервисов» укажите `https://oauth.yandex.ru/verification_code`
   (нужно для ручного получения токена).
4. Скопируйте **ClientID**.
5. Откройте в браузере:
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>`
   и скопируйте выданный токен.

### 3.2. Ключ шифрования

Токен хранится в БД зашифрованным, ключ берётся только из окружения:

```bash
openssl rand -base64 32        # сгенерировать ключ
```

Положите его в `.env` на сервере как `BACKUP_ENCRYPTION_KEY=...`. Подробнее — раздел 5.

### 3.3. Настройка в админке

Админка → вкладка **Бэкап**:

1. Вставьте OAuth-токен и папку на Диске (по умолчанию `/tattoo-backups`).
2. Нажмите «Проверить подключение» — должен появиться зелёный статус.
3. Нажмите «Создать бэкап» — через несколько секунд в списке появится копия с датой, статусом и составом.

### 3.4. Cron (резервный путь)

На сервере в `/home/server/website-tattoos/.env` (рядом с `docker-compose.yml`) добавьте:

```properties
YANDEX_DISK_TOKEN=<тот же токен>
YANDEX_DISK_DIR=/tattoo-backups
```

Crontab (ежедневно в 3:00):

```cron
0 3 * * * cd /home/server/website-tattoos && ./scripts/backup.sh >> /var/log/website-tattoos-backup.log 2>&1
```

Скрипт делает локальную копию (дамп + архив + конфиги + sha256), затем загружает дамп и архив на Диск.

## 4. Настройки

### 4.1. Приложение (`application.properties`)

| Свойство | По умолчанию | Переменная окружения | Что делает |
|---|---|---|---|
| `app.backup.mysqldump-path` | пусто (автопоиск) | `APP_BACKUP_MYSQLDUMP_PATH` | путь к `mysqldump`; пусто → поиск `mysqldump`/`mariadb-dump` в `PATH` и типовых каталогах |
| `app.backup.mysql-path` | пусто (автопоиск) | `APP_BACKUP_MYSQL_PATH` | путь к `mysql` (восстановление); пусто → поиск `mysql`/`mariadb` |
| `app.backup.include-images` | `true` | `APP_BACKUP_INCLUDE_IMAGES` | включать архив картинок |
| `app.backup.dump-timeout-minutes` | `15` | `APP_BACKUP_DUMP_TIMEOUT_MINUTES` | таймаут дампа |
| `app.backup.restore-timeout-minutes` | `20` | `APP_BACKUP_RESTORE_TIMEOUT_MINUTES` | таймаут восстановления БД |
| `app.backup.keep` | `3` | `APP_BACKUP_KEEP` | сколько последних копий хранить на Диске; `0` — не ротировать |
| `app.backup.cron` | `0 0 3 * * *` | `APP_BACKUP_CRON` | расписание автобэкапа (Spring cron, 6 полей, время сервера) |
| `backup.encryption.key` | `${BACKUP_ENCRYPTION_KEY:}` | `BACKUP_ENCRYPTION_KEY` | AES-256 ключ для токена Яндекс.Диска |
| `app.storage.upload-dir` | `uploads/images` | `APP_STORAGE_UPLOAD_DIR` | каталог картинок (он же архивируется и восстанавливается) |

### 4.2. Настройки в БД (`backup_settings`)

| Поле | Смысл |
|---|---|
| `provider` | всегда `YANDEX_DISK` |
| `yandex_token` | OAuth-токен, зашифрован AES-GCM (Base64, IV+данные) |
| `backup_dir` | папка на Диске, по умолчанию `/tattoo-backups` |
| `enabled` | включает автобэкап в планировщике |
| `last_backup_at` | время последнего прогона (успешного или нет) |
| `last_backup_status` | `SUCCESS` или `FAILED` |
| `updated_at` | время изменения настроек |

Токен можно только задать/заменить: пустое поле в форме означает «оставить прежний».

### 4.3. Переменные cron-скрипта

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `YANDEX_DISK_TOKEN` | — | токен; без него шаг загрузки пропускается |
| `YANDEX_DISK_DIR` | `/tattoo-backups` | папка на Диске |
| `BACKUP_ROOT` | `~/backups/website-tattoos` | куда складывать локальные копии |
| `KEEP_LAST` | `7` | сколько локальных копий хранить |
| `DB_CONTAINER` / `SERVICE_CONTAINER` | `db` / `service` | имена контейнеров |
| `YANDEX_API_BASE` | `https://cloud-api.yandex.net/v1/disk` | переопределение API (для тестов) |

## 5. Ключ шифрования

- Ключ — Base64 от 32 байт, AES-256-GCM; проверяется при старте `CryptoService` (неверная длина —
  приложение не поднимется, это защита от «тихого» шифрования пустым ключом).
- В проде ключ приходит **только** из `BACKUP_ENCRYPTION_KEY` (`.env` → `docker-compose.yml`).
  Деплой-пайплайн проверяет наличие переменной до `docker pull`.
- В `application-dev.properties` и `application-test.properties` лежат отдельные локальные ключи.
- **Смена ключа делает сохранённый токен нечитаемым.** После смены откройте админку и введите токен заново.
- При переезде со старой схемы (ключ лежал в `application.properties`) положите старое значение в
  `BACKUP_ENCRYPTION_KEY` — сохранённый токен продолжит расшифровываться.
- Старый ключ остался в истории git — его следует считать скомпрометированным и перевыпустить
  (вместе с OAuth-токеном).

## 6. Создание бэкапа

### 6.1. Кнопка в админке

«Создать бэкап»:

1. `POST /admin/backup/create` занимает слот и возвращает ответ сразу.
2. В фоне (`backupExecutor`, один поток): дамп БД → архив картинок → создание папки на Диске →
   загрузка файлов → ротация.
3. UI опрашивает `GET /admin/backup/status` каждые 3 секунды (до 6 минут) и показывает результат.
4. По завершении обновляются `last_backup_at` / `last_backup_status` и перезагружается блок копий.

Если бэкап уже идёт — кнопка вернёт «Бэкап уже выполняется — дождитесь завершения». Если идёт
восстановление — «Идёт восстановление из копии».

### 6.2. Планировщик

`BackupScheduler` срабатывает по `app.backup.cron` (по умолчанию ежедневно в 03:00 по времени сервера;
в контейнере это обычно UTC — при необходимости задайте `TZ` или сдвиньте cron). Перед запуском проверяет:

- `enabled = true` в `backup_settings`;
- токен задан;
- нет выполняющейся операции.

Если что-то не так — пишет причину в лог и пропускает запуск. Ошибка планировщика не останавливает
приложение: исключение логируется.

### 6.3. Cron-скрипт

`scripts/backup.sh` (6 шагов):

1. Дамп БД через `docker exec <db> mysqldump ... | gzip` → `db.sql.gz`.
2. Архив картинок: путь volume определяется через `docker inspect`, затем `tar -czf` → `images.tar.gz`.
3. Копия `docker-compose.yml` и `.env.example`.
4. `sha256sum` для проверки целостности.
5. Локальная ротация (`KEEP_LAST=7`).
6. Загрузка на Диск (если задан `YANDEX_DISK_TOKEN`): создание папки, двухшаговая загрузка
   (GET `upload` → PUT на выданный URL), имена — `db_<дата>.sql.gz` / `images_<дата>.tar.gz`.

Если загрузка на Диск не удалась, скрипт завершается с кодом 1, но локальная копия остаётся.
Ошибки не «проглатываются» — cron/мониторинг увидят ненулевой код.

Локальная копия лежит в `~/backups/website-tattoos/<дата>/` и содержит:

```
db.sql.gz          images.tar.gz        docker-compose.yml
.env.example       SHA256SUMS
```

## 7. Файлы на Диске и локально

На Диске копии лежат **плоско** в `backup_dir` (`/tattoo-backups` по умолчанию):

```
/tattoo-backups/
├── db_2026-10-25_03-00-00.sql.gz
├── images_2026-10-25_03-00-00.tar.gz
├── db_2026-10-24_03-00-00.sql.gz
├── images_2026-10-24_03-00-00.tar.gz
└── ...
```

Такой формат выбран потому, что админка умеет скачивать, удалять и восстанавливать конкретный файл,
а пара определяется по одинаковому `<дата>`. Посторонние файлы в папке игнорируются (не показываются
и не удаляются ротацией).

Локально cron-скрипт хранит копии по каталогам с датой — это независимый контур (3-2-1: прод,
локальные копии на сервере, offsite на Диске).

## 8. Ротация

### 8.1. На Диске

После каждой успешной загрузки `BackupService.rotateRemoteBackups`:

1. Получает список файлов в `backup_dir`.
2. Группирует их в копии по дате (`db_*` + `images_*`).
3. Оставляет последние `app.backup.keep` копий (по умолчанию **3**).
4. **Никогда не удаляет последнюю полную копию** (есть и дамп, и картинки), даже если после неё были
   только неудачные попытки или появилась неполная копия.

Следствия:

- три неудачных прогона подряд не удаляют ни одной успешной копии (неудачи не создают файлов,
  а ротация запускается только после успешной загрузки);
- если самая новая копия неполная (например, без архива картинок), предыдущая полная сохраняется;
- `app.backup.keep=0` отключает ротацию полностью;
- удаление на Диске — через API с `permanently=false`, то есть файл попадает в корзину Диска, а не
  стирается безвозвратно.

Ошибки удаления не ломают бэкап: они только логируются.

### 8.2. Локально

`scripts/backup.sh` хранит `KEEP_LAST=7` последних каталогов в `BACKUP_ROOT` и удаляет более старые.
Ротация локальных копий никак не связана с облачной.

## 9. Восстановление

### 9.1. Из админки

В блоке «Резервные копии» у каждой копии есть кнопка **Восстановить**.

Порядок:

1. UI просит ввести слово «ВОССТАНОВИТЬ» (защита от случайного клика).
2. `POST /admin/backup/restore` с `stamp` и `confirmation=RESTORE`.
3. В фоне: скачивание `db_<дата>.sql.gz` и (если есть) `images_<дата>.tar.gz` с Диска.
4. Дамп распаковывается и заливается в текущую БД клиентом `mysql`
   (host/port/база/пользователь — из `spring.datasource.*`, пароль — через `MYSQL_PWD`).
5. Архив картинок распаковывается в `app.storage.upload-dir`; существующие файлы перезаписываются,
   записи вне `images/` и попытки path traversal отвергаются.
6. UI опрашивает `GET /admin/backup/restore/status` (до 10 минут) и показывает результат.

**Это деструктивно:** текущая БД перезаписывается. Отката нет — перед восстановлением сделайте
свежий бэкап текущего состояния.

Особенности:

- Если в копии нет дампа БД — восстановление отклоняется («восстанавливать нечего»).
- Если нет архива картинок — восстанавливается только БД.
- Картинки, которых не было в архиве, **не удаляются** (восстановление — merge, а не «заменить всё»).
- Пока идёт восстановление, создать бэкап нельзя, и наоборот.
- Нужен клиент `mysql` (в Docker-образе установлен `mysql-client-8.0`).

### 9.2. Вручную (скрипт)

1. Скачайте нужную пару файлов из админки (кнопка «Скачать» отдаёт временную ссылку Яндекс.Диска)
   или через `rclone`/`curl`.
2. Разверните на тестовой БД: `scripts/restore.sh` (проверка sha256, `zcat db.sql.gz | mysql ...`,
   распаковка архива картинок).
3. Убедитесь, что сайт открывается и картинки на месте.
4. Только после проверки — восстанавливайте прод.

Бэкап, который ни разу не восстанавливали, бэкапом не считается: раз в месяц прогоняйте restore
на отдельной БД и проверяйте результат.

## 10. Статусы и мониторинг

### 10.1. Где смотреть

| Источник | Что показывает |
|---|---|
| Админка → Бэкап | дата и статус последнего запуска, список копий с составом, статусы «Успешно»/«Неполная» |
| `backup_settings.last_backup_at` / `last_backup_status` | последний прогон (переживает рестарт) |
| `GET /admin/backup/status` | текущее состояние операции в памяти (`IDLE`/`RUNNING`/`SUCCESS`/`FAILED`, сообщение, дата) |
| `GET /admin/backup/restore/status` | то же для восстановления |
| Логи приложения | `BackupWorker`, `RestoreWorker`, `BackupService`, `YandexDiskService` |
| Лог cron | файл, указанный в crontab (`/var/log/website-tattoos-backup.log`) |

Состояние операций хранится **в памяти** и сбрасывается при рестарте (`IDLE`); исторический статус
последнего прогона — в БД.

### 10.2. Коды и сообщения

| Сообщение | Значение |
|---|---|
| `SUCCESS` | копия загружена (возможно, без картинок — тогда в UI «Неполная») |
| `FAILED` | прогон не удался, причина — в логе и в `message` статуса |
| `RUNNING` | операция выполняется |
| `IDLE` | операций не было с момента старта приложения |

## 11. HTTP API админки

Все эндпоинты — под `/admin/**` (роль `ADMIN`). Ответы — JSON, кроме фрагментов.

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| GET | `/admin/backup/fragment` | — | HTML-фрагмент блока настроек и копий |
| POST | `/admin/backup/save` | поля `BackupSettings` (`yandexToken`, `backupDir`, `enabled`) | HTML-фрагмент |
| POST | `/admin/backup/test` | — | `{success, message\|error}` |
| POST | `/admin/backup/create` | — | `{success, started}` или `{success:false, error}` |
| GET | `/admin/backup/status` | — | `{state, running, message, dir, startedAt, finishedAt}` |
| GET | `/admin/backup/download` | `fileName` | `{success, url}` (временная ссылка Диска) |
| POST | `/admin/backup/delete` | `fileName` | `{success, error?}` (в корзину Диска) |
| POST | `/admin/backup/restore` | `stamp`, `confirmation=RESTORE` | `{success, started}` или `{success:false, error}` |
| GET | `/admin/backup/restore/status` | — | `{state, running, stamp, message, startedAt, finishedAt}` |

Пример проверки статуса:

```bash
curl -s -b 'JSESSIONID=...' https://site.example/admin/backup/status | jq
```

## 12. Диагностика ошибок

| Симптом | Причина | Решение |
|---|---|---|
| `mysqldump не найден` | нет клиента MySQL | в Docker-образе он есть; локально `sudo apt install mysql-client` или `app.backup.mysqldump-path`. Без root: `apt-get download mysql-client-core-8.0 && dpkg -x *.deb .tools/mysql-client-core` |
| `Plugin caching_sha2_password could not be loaded` | клиент MariaDB не умеет аутентификацию MySQL 8 | образ должен быть на `mysql-client-8.0` (текущий Dockerfile); либо указать путь к клиенту MySQL 8 |
| `mysqldump завершился с кодом 1045` | неверные логин/пароль БД | проверьте `SPRING_DATASOURCE_*` |
| `Yandex.Disk ... 401` | токен неверный/просрочен | перевыпустите токен, сохраните в админке |
| `Yandex.Disk ... 403` | у приложения нет прав `cloud_api:disk.write` | добавьте право в OAuth-приложении и перевыпустите токен |
| `Yandex.Disk ... 404` | нет папки или файла | папка создаётся автоматически при загрузке; проверьте `backup_dir` |
| «Бэкап уже выполняется» | идёт бэкап или восстановление | дождитесь завершения (`/admin/backup/status`) |
| «Копия не найдена на Диске» | файлы удалены/ротация/неверная дата | обновите список, проверьте папку на Диске |
| «В копии нет дампа БД» | неполная копия (только картинки) | выберите другую копию |
| «Клиент mysql не найден» при восстановлении | нет клиента в окружении | в образе он есть; локально задайте `app.backup.mysql-path` |
| `mysql не завершился за N мин` | огромный дамп/медленная БД | увеличьте `app.backup.restore-timeout-minutes` |
| «Не удалось распаковать картинки» / «Недопустимый путь в архиве» | повреждённый архив или path traversal | проверьте архив вручную; такой архив не распаковывается |
| Нет копий в списке, хотя cron отработал | файлы со старыми именами (`<дата>_db.sql.gz`) | обновите `scripts/backup.sh` — теперь имена `db_<дата>.sql.gz`; старые файлы считаются посторонними |
| Долго висит статус `RUNNING` | операция упала без обновления (редко) | проверьте лог; после рестарта статус сбросится в `IDLE` |

Полезные команды на сервере:

```bash
docker exec service mysqldump --version     # клиент в образе
docker exec service mysql --version
docker compose logs --tail=200 service | grep -i -E 'backup|restore|yandex'
ls -lh ~/data/images | head                 # картинки
docker exec db mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e 'SHOW DATABASES;'
```

## 13. Безопасность

- Токен Яндекс.Диска хранится в БД в зашифрованном виде (AES-256-GCM, случайный IV на каждое
  шифрование), ключ — только в окружении.
- UI/эндпоинты бэкапа доступны только роли `ADMIN` (правило `/admin/**`).
- Восстановление требует явного `confirmation=RESTORE` (защита от случайного вызова), но **не является
  CSRF-защитой**. В проекте CSRF пока отключён — до его включения (пункт H1 код-ревью) не выкладывайте
  восстановление в публичный доступ без дополнительной защиты.
- Дампы **не шифруются** на Диске и содержат персональные данные и bcrypt-хеши паролей. Ограничьте
  доступ к папке на Диске; при необходимости шифруйте файлы перед загрузкой.
- Удаление копии на Диске отправляет файл в корзину (`permanently=false`), а не стирает безвозвратно.
- Ключ шифрования и OAuth-токен — секреты: не коммитьте `.env`, не печатайте токен в логах.

## 14. Ограничения

- Нет инкрементальных бэкапов — каждый прогон делает полный дамп и полный архив картинок.
- Нет истории запусков в БД: хранится только последний статус; список копий строится по файлам на Диске,
  поэтому неудачные попытки в списке не видны (они не создают файлов).
- Нет уведомлений (email/Telegram) об упавшем бэкапе — только лог и статус `FAILED`.
- Восстановление не делает откат и не удаляет «лишние» картинки.
- Один прогон — один поток; параллельные бэкапы сознательно запрещены.
- Время планировщика — время JVM/контейнера (обычно UTC); при необходимости настройте `TZ`.
- Шифрование бэкапов на Диске не выполняется.
- Ротация ориентируется на имена файлов; переименованные вручную файлы в расчёт не попадают.

## 15. Развёртывание и обновление

1. Образ приложения собирается из `Dockerfile`: runtime-стадия — Ubuntu (`eclipse-temurin:21-jre-jammy`)
   с `mysql-client-8.0` (даёт `mysqldump` и `mysql`, поддерживающие `caching_sha2_password` MySQL 8).
2. `docker-compose.yml` передаёт в контейнер `BACKUP_ENCRYPTION_KEY` и `APP_STORAGE_UPLOAD_DIR`.
3. Деплой-пайплайн (`.github/workflows/deploy.yml`) до `docker pull` проверяет в `.env`:
   `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `BACKUP_ENCRYPTION_KEY`.
4. Скрипты `scripts/backup.sh` и `scripts/restore.sh` копируются в `/home/server/website-tattoos/scripts/`
   — оттуда их запускает cron.
5. После деплоя проверьте: `docker exec service mysqldump --version` и один ручной бэкап из админки.

Первичная настройка на новом сервере:

```bash
cp .env.example .env && $EDITOR .env      # MYSQL_*, MAIL_*, BACKUP_ENCRYPTION_KEY, YANDEX_DISK_TOKEN
docker compose up -d
```

## 16. Чек-лист проверки

- [ ] `BACKUP_ENCRYPTION_KEY` задан в `.env` (32 байта Base64), деплой проходит preflight.
- [ ] Токен сохранён в админке, «Проверить подключение» — успешно.
- [ ] Кнопка «Создать бэкап» → статус `SUCCESS`, на Диске появились `db_*` и `images_*` с одинаковой датой.
- [ ] В списке копия отображается с датой, статусом «Успешно», размерами БД и картинок.
- [ ] После 4 прогонов на Диске осталось 3 копии (ротация), последняя успешная на месте.
- [ ] Неудачный прогон (например, временно неверный токен) не удалил успешные копии.
- [ ] Восстановление на тестовой БД: кнопка «Восстановить», ввод «ВОССТАНОВИТЬ», статус `SUCCESS`,
      данные и картинки на месте.
- [ ] Cron на сервере: `./scripts/backup.sh` завершается с кодом 0, файлы на Диске видны в админке.
- [ ] Логи не содержат паролей и токенов.

## 18. Возможные доработки

- Шифрование архивов на Диске (например, `gpg`/`age`) и хранение ключа отдельно от приложения.
- История запусков в БД (`backup_run`) с отображением неудачных попыток в UI.
- Уведомления об `FAILED` (email/Telegram/webhook).
- Инкрементальные бэкапы картинок (rsync/restic) при росте объёма.
- Автоматическая проверка восстановления (раз в месяц на тестовой БД).
- Ограничение частоты и CSRF для деструктивных эндпоинтов.
- Ротация с учётом квоты Яндекс.Диска и срока хранения (не только количества).
