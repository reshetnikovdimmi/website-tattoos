# Бэкапы: как устроено и как пользоваться

Бэкап состоит из двух файлов за один прогон:

| Файл | Что внутри |
|---|---|
| `db_<дата>.sql.gz` | полный дамп MySQL (`mysqldump --single-transaction`) |
| `images_<дата>.tar.gz` | архив папки `app.storage.upload-dir` (по умолчанию `/app/img/images`) |

Оба кладутся в папку на Яндекс.Диске (`/tattoo-backups` по умолчанию) с одинаковым префиксом-датой,
поэтому их легко сопоставить. Локальная копия (3-2-1) делает `scripts/backup.sh`.

## Три способа запуска

| Способ | Где | Когда работает |
|---|---|---|
| Кнопка «Создать бэкап» | админка → Настройки → Бэкап | пока приложение живо |
| Планировщик в приложении | `BackupScheduler`, cron `app.backup.cron` | если включён чекбокс «Включить автоматический бэкап» и задан токен |
| Cron на сервере + `scripts/backup.sh` | хост, вне контейнера | даже если приложение упало |

Кнопка и планировщик используют один и тот же `BackupService`, защищённый блокировкой: два бэкапа
одновременно не запустятся (второй получит «Бэкап уже выполняется»). Кнопка запускает работу в фоне
(`BackupWorker`, один поток `backupExecutor`) и опрашивает `/admin/backup/status`, поэтому HTTP-запрос
не висит минутами.

## Настройки

`application.properties` (значения по умолчанию):

```properties
app.backup.mysqldump-path=       # пусто = автопоиск mysqldump / mariadb-dump в PATH
app.backup.include-images=true   # архив картинок
app.backup.dump-timeout-minutes=15
app.backup.keep=14               # сколько последних прогонов хранить на Диске (0 = не удалять)
app.backup.cron=0 0 3 * * *      # каждый день в 3:00 по времени сервера
```

Настройки самого Диска (токен, папка, включение) — в админке, таблица `backup_settings`.
Токен хранится в БД в зашифрованном виде (AES-GCM).

### Ключ шифрования

`backup.encryption.key` берётся **только из окружения**: `BACKUP_ENCRYPTION_KEY` (base64, 32 байта).

```bash
openssl rand -base64 32
```

- В `application-dev.properties` лежит фиксированный dev-ключ — для локального запуска.
- В `application-test.properties` — тестовый.
- В проде ключ передаётся через `.env` → `docker-compose.yml`; деплой проверяет его наличие до `docker pull`.

Смена ключа делает ранее сохранённый токен нечитаемым: после смены нужно заново ввести OAuth-токен
в админке. При переезде со старой схемы (ключ был в `application.properties`) просто положите **старое**
значение в `BACKUP_ENCRYPTION_KEY` — сохранённый токен продолжит расшифровываться.

### Ротация на Диске

После успешной загрузки `BackupService.rotateRemoteBackups` смотрит список файлов в папке бэкапов,
группирует их по дате из имени и удаляет всё, кроме последних `app.backup.keep` групп (по умолчанию 14).
Ошибки удаления не ломают бэкап — только пишутся в лог.

## Восстановление

1. Скачать нужную пару файлов: админка → Бэкап → «Скачать» (или `scripts/backup.sh`/`rclone` с Диска).
2. Развернуть на тестовом контейнере и прогнать `scripts/restore.sh` (БД + картинки).
3. Только после проверки — на прод.

Бэкап, который ни разу не восстанавливали, бэкапом не считается: раз в месяц прогоняйте restore
на отдельной БД и проверяйте, что сайт открывается и картинки на месте.

## Диагностика

| Симптом | Причина / что делать |
|---|---|
| «mysqldump не найден» | нет клиента MySQL. В Docker он есть (`mariadb-client` в Dockerfile); локально: `sudo apt install mysql-client`. Без root: `apt-get download mysql-client-core-8.0 && dpkg -x *.deb .tools/mysql-client-core` и указать `app.backup.mysqldump-path` |
| «Диск недоступен», 401 | неверный/просроченный OAuth-токен — сохраните новый в админке |
| «Бэкап уже выполняется» | идёт другой прогон (кнопка или планировщик), дождитесь |
| Статус `FAILED` в админке | смотрите лог: `docker compose logs service` / файл лога; в `backup_settings.last_backup_status` |
| Планировщик не срабатывает | выключен чекбокс, не задан токен, или приложение не работает; проверьте `app.backup.cron` и часовой пояс контейнера |

Статус последнего прогона: `backup_settings.last_backup_at` / `last_backup_status` (`SUCCESS`/`FAILED`).
